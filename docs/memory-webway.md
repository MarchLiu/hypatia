# 记忆的网道

我是2026年春天才开始开发hypatia的。但是这个项目承载了我长久以来的一些想法。

## 故事开始之前

2022年离开 csdn 人工智能组以后，我开始接触LLM。从一开始 Context Length 就成了一个重要的挑战。

彼时 LLM 的 Context Length 往往局限于 4096 到 8000 tokens。看起来很多，但是同行们肯定可以理解，这个长度实在太容易饱和。

众所周知，RAG 很快出现了，最初的RAG是非常粗糙的，一般就是按固定长度切割。即使不考虑实际情况，这对我来说也过于粗糙了。

很快我就开始尝试使用关系型数据库实现更好的检索增强，这也经过了很多次探索。而 Hypatia 可以看作是这些年的各种 AI 知识库的一个经验总结。

为 AI 引入图结构的增强搜索，并不是我的独创。很多同行都在做类似的工作。而我的工作，基于十多年前就开始的，关于递归查询和动态结构存储的探索。

在我看来，这才是AI增强检索技术最完美的方向。显式定义关系的图，和基于几何关系进行相似度匹配计算的嵌入向量，以及基于关键字的全文检索的组合，可以构成相当完备的知识发现能力。我的目标不仅仅是记录日常的工作任务，这些工作记录可能我一年也不会超过十万条记录，但是我还有大量需要整理检索的论文、文档等资料。我需要AI帮我整理的信息可能达到亿级水平。

## 知识的亚空间和无尽记忆的网道

2026 年的主流 AI 支持更长的 Context Length，也有更强的理解能力和更稳定的输出控制。最初基于我常用的 GLM 5.1，我开始开发 Hypatia，
而 Deepseek V4 pro 发布后，我们有了一个 1MB 上下文的高质量模型可用，这为无限记忆系统提供了可靠的基石。

Hypatia 旨在尽量不损失信息的情况下，让有限记忆的 AI 可以使用（相对）无限长度的知识内容。因此，完整的生态包含

- 一个图数据库，hypatia 实际上组合了 duckdb 和 sqlite，duckdb 管理向量索引和图模型，sqlite 实现全文检索
- JSE 规范，通过一个符合 JSE 规范的查询语言，将数据库细节和知识检索隔离开，
- hypatia cli 程序，提供访问接口，允许在业务层面访问和管理书架（shelves）和图形态的知识，无需关注数据库底层
- hypatia skill，告诉 AI Agent 如何使用 hypatia 读写内容
- hypatia-memory skill，告诉 AI Agent 如何集成 hypatia，将日常的工作记录自动的写入数据库，并且自动的梳理为有条理的知识图谱

在这个体系下，我日常工作中，几乎不会主动干涉hypatia的运作，只有我的Agent提示“已写入hypatia”或者“从 hypatia 中检索xxx”的时候，我才会看到它的存在。

但是，有时候我也会主动指示 AI ，“读一下 hypatia，寻找关于 xxx 的记忆，用于完成 xxx 任务”这样的句式可以显示的提醒智能体基于长期记忆工作。

### 举个例子

我在运维一个不大的内部集群，我编写了一个文档，列清每个节点的ip、职责描述、内部架构，节点间关系。然后我发给 opencode，让它写到 hypatia 中。

这其中比较重要的是，我在一台机器上运行了ansible的master，所有的ops工作，必须写成 ansible playbook，通过master节点下发给实际目标运行。

这之后的一两个月以来，大部分情况下，当我需要AI进行运维操作时，它会正确的找到必要的记忆，按照我的规划去执行。偶尔我也看到 opencode 试图直接用 ssh 连接服务器。这个时候我只需要打断它，提醒它“在hypatia中查找运维工作有关的信息，再继续刚才的任务”。甚至有时候仅仅是“读一下hypatia”即可达到目标。

只有我需要读一些书或者文档时，才会明确要求Agent将这些内容拆解为条目和三元组，写入到hypatia。但是这样的事情并不长发生。一般来说，长时工作的 Agent，例如 openclaw 或 harness 更适合做这样的工作。

回报是明显的，我可以明确的看到，AI如果没有认识到需要查询 Hypatia，它会表现出有限记忆的局限性，不过，虽然记住我所有的工作准则对于朴素的 Agent memory 机制有点困难，记住要经常查 hypatia 并不难。

对我来说，hypatia 首先是一个日用工具，我希望它对我的使用负担越轻越好，回报效果越大越好。在实际使用中，除了偶尔要求Agent回忆，它对我几乎是无感的。

换句话说，只有 Agent 忘记要查 hypatia的时候，我才会想起来我需要它。


### Agent 中立

Hypatia 并不局限于某个单独的Agent，我在我工作机的每一个Agent上都部署了Hypatia，openclaw、harness、opencode、claude等等。所以我可以方便的在不同的工具之间传递信息。

## 代价呢？

毫无疑问，在每个对话后总是要专门判断这些内容是否形成了一条知识，是否需要和既有的内容建立关联，确实需要更多的token。目前看，这是值得的。

使用 duckdb 作为主数据库，主要是为了内置的向量索引和 PG 风格的查询语言，JSON、大文本支持、递归查询，带来了巨大的回报。但是代价也是明显的，我的 default shelves 现在已经有 4GB了。这显然不太经济。

首先，我并不想转回纯文本，功能丰富的关系型数据库带来了极大的便利。但是我真的在考虑使用单一的 sqlite 代替 duckdb+sqlite 的组合。主要的麻烦主要是：

- 我的设计依赖 json 的 contains 查询。这个功能在 PostgreSQL 的 jsonb 类型中有强大的支持，duckdb提供了有限的支持，而sqlite几乎完全无法实现
- SQLite 的查询风格和PG比较远，我最初的开发借鉴了这些年来基于 PG 的项目经验
- 虽然hypatia现在只有两百多 stars，但是我并不确定是不是真的已经有朋友在使用它，既然如此，我在做基础设施改动时，要有自动化的升级过程。
- 目前看体积主要来自向量索引，我换用 sqlite，未必会换来本质上的改善，这个工作是否值得有待验证

如果你有多个机器，希望在它们之间共享记忆，hypatia的体系就不那么好用了。实际上我的工作中开发了一套远比hypatia强大的图数据库系统，它是一个内部项目，hypatia强调的是可以部署在每个电脑本地，而那个内部系统是一个基于 PostgreSQL 的服务，我在学院的某个研究性的生产力工具上实验过使用这个图数据库服务器作为远程的记忆系统，效果也不错。而如果是hypatia，分布式的体系就决定了，想要动态合并，需要一些艺术，我暂时还没有实现它的动力。
